# 会議室画像差し替え時の後片付け

基準コミット: `8ee56c4141d8c8e0e54f65de98ab092ce2205d30`

## 変更内容と影響範囲

- 管理画面のアップロード・RPC更新・後片付けを `src/lib/replace-room-image.ts` に抽出。
- 更新前にDBから現在の画像パスを取得し、古い画面のpropsだけで削除対象を決めない。
- RPC成功後、自室の `rooms/{ID}/{UUID}.jpg|jpeg|png|webp` に一致する旧画像だけを候補にする。Seed画像、共有フォルダ、他室のパス、同じパス、未登録の画像は対象外。
- 非公開・非稼働の会議室を含め、DBに同じパスの参照が残っていれば削除しない。参照確認に失敗した場合も削除しない。
- RPC失敗時は新規アップロードの削除を維持。ただし、応答だけ失われてDBでは更新済みの場合に備え、新規画像にも参照確認を行う。
- 後片付け失敗ではDB更新を取り消さず、警告を表示。通信例外でもボタンの待機状態を解除する。
- StorageのSELECT権限を管理者に追加し、削除用のrestrictive RLSでSeed・参照中画像を保護する。`meeting-room-images` 以外のバケットには制約を追加しない。
- 既存RPCの引数・戻り値、画像形式・サイズ制限、見積もり・認証処理は変更しない。
- CIに `npm test` を追加し、新規回帰テストを既存E2Eと同じワークフローで実行する。

## 適用順序

1. `supabase/migrations/202610090001_protect_room_image_cleanup.sql` を適用。
2. アプリケーションをデプロイ。

この変更には上記マイグレーションが必要。認証済み管理者によるSeedや参照中画像の手動削除もRLSで拒否される。Service roleは引き続きRLSを迂回する。

## 運用上の範囲

既に蓄積している未使用ファイルは一括削除しない。通信障害・後片付け失敗時は、安全のためファイルが残ることがある。DB更新とStorage削除は別リクエストであり、厳密な単一トランザクションではない。同時差し替えでは中間画像が残る可能性がある。削除中の古いパスを別の管理処理から再割当てする操作までは直列化しないため、そのような同時書込みを行う運用ではサーバー側の排他・削除キューを別途設計する必要がある。
